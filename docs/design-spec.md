## 0. 这一版改了什么

v1.0 的价值主张是「多设备 iCloud 同步」。**这个假设当时没有任何证据支撑**，是从最初一句需求直接接下来的。

本版基于 **1214 条中国区竞品真实评论**（12 款念佛/定课类 App，经 App Store 公开接口抓取于 2026-07）重新定位。原始存档未随仓库公开——批量转载他人评论在版权与平台条款上站不住，与本项目的发心相违；下述结论与引用的代表性评论即为全部依据。核心结论：

| 原假设 | 实证结果 |
|---|---|
| 「换手机丢数据」是头号痛点 | **是真痛点，但是焦虑点不是愤怒点**。几乎全部出现在 4-5 星好评的「唯一遗憾」里，差评中占 14.8% 排第三 |
| — | **头号差评是闪退/卡顿，占 36.7%** |
| — | **「没有广告」被感谢 60 次，情感强度碾压一切功能** |
| 用户要多设备同步 | 用户要的是**备份**。真正的多设备诉求是 **Apple Watch**（4 条），不是 iPad（1 条） |
| 禅modo 是护眼的锦上添花 | **是宗教身份隐私的刚需**，两条独立评论动机一致：不想让同事知道自己念佛 |
| 农历排班太重，可以后置 | 是被表扬的功能，且用户还嫌不够（要十斋日、佛诞日） |

**2.1 补充**（第二轮实证，抓取 9 款竞品 App Store 官方描述交叉验证）：

| 原假设 | 实证结果 |
|---|---|
| 功课类目 = 念佛/诵经/打坐/拜佛 | **漏了「持咒」和「抄经」**。持咒在三款竞品中均为一等公民，评论中大悲咒/心咒/往生咒高频（§6.6） |
| 内置模板应带「合理默认目标值」，是差异化点 | **方向错误。9 款竞品无一预设数字**，全部「可自定义目标」。改为目标留空 +『108』可选 chip（§6.6） |
| — | **批量增加（+108 等）是市场标配**，竞品最多评论那款提供 7 档步长。缺此项会被直接比出劣势 |
| 竞争对手是别的 App | **是实体计数器**。「等我买了三千计数的就不用你了」——这条同时论证了 Apple Watch 的价值（§14.3） |

## 1. 定位

### 1.1 价值主张

竞品解决「数据不丢」的办法是**账号 + 服务器**，而服务器正是它们崩溃的根源。差评高频出现「根本登陆不上」「微信登录报错」「登录不上去，导致之前的记录都没有了」。

最有力的一条证据，来自竞品「八万四千」的一则 **5 星**长评：

> 「今天开始出现各种故障，估计是服务器主磁盘缓存已满……由于八万四千项目现阶段在**商业上没有盈利的方式，也无后续融资**……请师兄们**及时做好数据备份，以防服务器突然关闭**。」

用户在评论区互相提醒：这个公益 App 的服务器快撑不住了，赶紧自己备份。

**所以零后端不是省事的技术选型，它是核心价值主张：**

1. **清净** — 无广告、无内购、无订阅、无推送营销。这是这个品类情感强度最高的诉求
2. **无账号** — 不注册、不登录、不要手机号。竞品的登录失败即数据失联，我们没有这个失效点
3. **不经我手** — 数据只在你的设备和你自己的 iCloud 私有库里。我看不到，也不可能弄丢
4. **稳** — 纯本地读写，断网完全可用。直接对着 36.7% 的闪退差评

### 1.2 目标用户

汉传佛教在家居士。**年长用户占比高**——竞品好评中明确出现「即使不会使用智能手机的老年人也会使用了」。这不是边缘人群，是主力人群之一（详见 §6.9 长辈模式）。

定课是长期、每日多次、高情感权重的行为。**丢数据是事故，不是 bug。**

### 1.3 竞品实证要点

| 发现 | 证据 | 对设计的要求 |
|---|---|---|
| 整屏可点是刚需 | 竞品缩小点击区后被差评：「拿手机边走路边计数，点击位置不对就会无效」 | 计数区必须整屏（§6.2） |
| 改错数字找不到入口 | 「急！我地藏经报错数字了，怎么修改啊，找半天没有这个功能！」 | 修正入口必须显眼（§6.4） |
| 音效/震动是防漏记的功能 | 「震动提示和声音提示任选，**有效防止漏记多记**」 | 不是装饰，是计数确认反馈（§6.2） |
| 不能设计数上限 | 「观音心咒的功课是在九位数，在限制百万之后需要不断重新建立」 | 累计值不设上限 |
| 交互式小组件已是入场券 | 「现在可以**直接在桌面操作小组件来加减数字**」 | 竞品已实现，必须有（§8.2） |
| 跨日清零频繁出错 | 「昨天的计数不会自动清零，除非今天报数才会更新」 | dayKey 设计正对此（§4.3） |
| 宗教隐私是真需求 | 「不想让别人知道，比如开大会的时候」「工作关系，不能让同事知道自己念佛」 | 隐藏模式 + 隐私锁进 v1（§6.5 §8.4） |
| 农历要更细 | 「如果再有**十斋日**的提醒就更方便了」「最好把日历添加上十斋日」 | 农历排班扩展（§8.1） |

## 2. 范围

### 2.1 v1 做什么

**核心闭环**：打开 → 看到今天要做什么 → 点一下 → 完成。**「打开到记完的耗时」是第一产品指标。**

- 定课项：内置模板（8 类，含**持咒**与**抄经**，见 §6.6）+ 完全自定义（含自定义经咒名称）
- 三种计量：计数 / 计时 / 勾选
- 三种录入：整屏计数器 / 基础计时器 / 手动补记
- **批量增加**（`+108` 等步长，市场标配，见 §6.6）
- **修正流水**（改错数字，显眼入口）
- **隐藏模式**（原「禅modo」，见 §6.5）
- **交互式桌面小组件**（v1 前三优先级，见 §8.2）
- 提醒：每日 / 每周 / **农历（初一十五、十斋日、佛诞日）**
- iCloud 备份同步 + 同步状态 + **诊断页**
- **自动备份到「文件」App，默认开启**
- 回顾月历 + **累计统计**
- 隐私锁（Face ID / Touch ID + Passcode 兜底）
- **长辈模式**（大字号 / 大点击区）
- **发心页**（见 §9.3）
- 音效 / 震动反馈
- 内置 1–2 段古来公有回向偈
- 简体 + **繁体中文**

### 2.2 推到 1.1

以下功能**有价值但不验证核心假设**，且占用大量开发量。先上线、看有没有人用，再决定。

| 功能 | 后置理由 |
|---|---|
| 修行日记 | 独立实体 + 一套 UI，非「记功课」核心 |
| 回向文库编辑 | v1 只内置公有偈颂；编辑器 + 同步实体较重 |
| CSV 导出 | v1 只留 JSON（JSON 是「永不丢」的备份网，CSV 只是便利） |
| Live Activity | 计时器基础版已足够；锁屏活动有更新预算限流风险（§12） |
| **iPad 适配** | 「同一套 SwiftUI 代码」是幻觉——`NavigationSplitView` + 双尺寸布局 + 双端测试。而实证只有 1 条 iPad 诉求 |
| **Apple Watch** | 实证需求比 iPad 强（4 条，含「一人血书求兼容 Apple Watch 版」）。**数字表冠即念珠、`mindfulness` 扩展会话可熄屏计数——这是这个 App 的终极形态。完整方案见 §8.6。1.1 首位，排在 iPad 之前** |

### 2.3 永不做

- 账号 / 注册 / 登录 / 服务器 — **这是竞品的死因，也是我们的定位**
- 广告 / 内购 / 订阅
- 排行榜 / 好友 / 攀比
- 徽章 / 彩带 / 红点催促 / 「失去连胜」话术
- 随机励志语录（版权风险 + 会腻）
- 课程学习模块

| 项 | 选择 |
|---|---|
| UI | SwiftUI |
| 持久化 | SwiftData |
| 同步 | CloudKit 私有数据库，`.modelContainer(cloudKitDatabase: .private(...))` |

**为什么 17.4**：SwiftData 要求 iOS 17；17.0–17.3 的 CloudKit 同步有已知缺陷。

**代价已量化并被接受**：StatCounter 中国区 2026-06，低于 iOS 17.4 占 13.8%。指数拟合半衰期 11.5 个月，上架时预计余 8–11%，2028 年中约 4%。产品方明确「不考虑老旧设备」——这个门槛每年自动减半，而 Core Data 的样板代码是永久负债。

## 4. 数据模型

### 4.1 核心原理：记账式 append-only

**问题**：CloudKit 冲突解决是**整条记录级的 last-writer-wins**。若把「今日总数」存成可变字段，两台设备各写各的，后写的会整条覆盖先写的——**用户念了 800 声，App 说 500**。

**解法**：每次修行结束生成一笔**独立、只增不改**的流水。各设备生成各自 UUID，主键永不碰撞，**永远不会互相覆盖**。今日总数 = 当天该功课所有流水**求和算出**，不是存储字段。

修改数字 = **追加一笔修正流水**（`source = .adjustment`，可正可负），不改原记录。

> 本质是 CRDT 的 PN-Counter。三轮评审一致确认这是整套方案最坚实的地基。
> **即使「多设备同步」不是主要场景，它依然是「永不丢」最廉价的正确实现。**

**写入粒度：结束时写一笔，不是每声一条。** 念佛 1000 声 = 1 条记录。重度用户 5 年累计仅几万条。
> ⚠️ **不要为了「更精细」改成 per-count 写入。**

### 4.2 实体

#### PracticeItem — 定课项

`id` / `name` / `iconName` / `colorHex` / `measureType`(count·duration·check) / `unit` / `dailyGoal`(计时存秒) / `scheduleRule` / `reminderTimes` / `sortOrder` / `isArchived` / `templateKey` / `createdAt` / `updatedAt`

`scheduleRule` 取值：`daily` / `weekdays:1,3,5` / `lunar:1,15` / `lunar:sixzhai` / `lunar:tenzhai` / `lunar:buddhaDays`

#### PracticeSession — 修行流水（append-only）

| 字段 | 说明 |
|---|---|
| `id` | UUID |
| `item` | 关系，可选 |
| `dayKey` | `yyyyMMdd` 整数 |
| `tzOffsetMinutes` | **记录发生时的时区偏移** |
| `amount` | 计时存秒；adjustment 可为负。**不设上限** |
| `startedAt` / `endedAt` | |
| `source` | counter · timer · manual · adjustment |
| `deviceName` | 让用户看懂「这笔是哪台设备记的」 |
| `note` | |
| `createdAt` | |

**只增不改不删。** 用户「删除」某笔 = 追加等额负数 adjustment。

#### DaySnapshot — 当日应做快照

**问题**：`dailyGoal`、`scheduleRule`、`isArchived` 都可变。若圆满判定实时重算，等于**用今天的配置评判过去每一天**——用户把目标从 300 改到 1000，**过去所有圆满日一夜全崩**。

**解法**：每天首次产生记录时冻结当天应做集合与目标。
`dayKey` / `requiredItems: [UUID]` / `goals: [String: Int]` / `createdAt`

**圆满判定一律读快照，永不实时重算。**

#### Dedication / DayDedication — 回向

v1 只内置古来公有偈颂，`Dedication` 暂不开放编辑（1.1）。`DayDedication` 为 append-only。

### 4.3 三个关键设计

**① dayKey 存整数，写入后永不重算**

从 UTC 绝对时刻反推「当时的本地日期」，必须知道**记录发生那一刻的时区**。用户在温哥华夜里念的佛，回国后一旦重算会整批偏一天。

- 每笔存 `tzOffsetMinutes`
- **`dayKey` 一旦写入永不重算**
- 修改「一日起始时间」**只对新记录生效**，不回溯

**② 一日起始时间可配置** — 默认 00:00，可设凌晨 3:00。夜课修到凌晨的用户希望算作「昨天」。

**③ 定课项只归档不真删** — 真删会让历史流水变孤儿。

### 4.4 缓存边界（硬性）

> 今日总数缓存**绝对不能**进 CloudKit，否则 §4.1 躲开的 LWW bug 原地复活。

| 数据 | 位置 | 同步 |
|---|---|---|
| 所有实体 | SwiftData + CloudKit | ✅ |
| 今日总数缓存（供小组件读） | **App Group UserDefaults** | ❌ **纯设备本地** |
| 用户设置 | `@AppStorage` + `NSUbiquitousKeyValueStore` | KVS，不进数据库 |

**缓存不得声明为 SwiftData 建模属性。** code review 时专门检查。

### 4.5 草稿与崩溃恢复

append-only 对**重复写入**毫无免疫力。若 Session 已写入但草稿未清，重开会记两遍。

1. 写入 Session 与清除草稿必须**同一事务**
2. 草稿携带预生成的 `sessionUUID`
3. 恢复前先查该 UUID 是否已存在，存在则丢弃草稿

### 4.6 SwiftData + CloudKit 硬性约束

属性必须**可选**或**有默认值**；**不能用** `@Attribute(.unique)`；关系必须**可选**且有**反向关系**；枚举用 String 原始值。

### 4.7 诚实声明：并非全无冲突

append-only 只解决**流水**冲突。**可变记录仍是整记录级 LWW**：`PracticeItem`（改名/改目标/排序）、`Dedication`。两台设备同时编辑同一项，后写的整条覆盖先写的（**不是字段级合并**）。

这可接受——低频且用户能感知，与「计数被静默吞掉」性质不同。但**不得对外宣称「全 App 无冲突」**。

## 5. 同步与备份

> **定位澄清**：这是**备份**，不是实时协作同步。宣传语、引导、优先级都据此确定。

### 5.1 用户可感知的行为

| 场景 | 行为 |
|---|---|
| 换手机 / 重装 | **记录自动回来**，这是核心承诺 |
| 未登录 iCloud | App **完全可用**，纯本地。登录后自动补传 |
| 飞行模式 | 本地立即生效，联网后自动上传 |
| 两台设备同时计数 | 各记各的，同步后**求和**，都不丢 |
| 删除某笔 | 追加负数修正流水 |
| 同步延迟 | 秒级到分钟级，**不保证实时**（用户要的是安心，不是秒级） |

### 5.2 同步状态可见性

CloudKit 是最终一致的，且**会静默失败**。不给反馈 = 用户以为数据丢了。

今日页底部常驻：`已备份 · 刚刚` / `有 2 条待上传 · 等待网络` / `备份出错 · 查看`

> 措辞用「**已备份**」而非「已同步」——对齐真实心智。

### 5.3 本地备份（默认开启）

「只有一台设备、没登 iCloud」恰恰是最危险的用户。**自动定期备份 JSON 到「文件」App**，默认开启，恢复流程极简。这是独立于 CloudKit 的第二条命。

### 5.4 诊断页

零后端 = 用户报「数据没了」时**无法远程排查**，而这正是核心卖点出问题的时候。

「我的」页提供：CloudKit 账号状态 / 上次成功备份时间 / 待上传条数 / 最近错误码 / 各实体记录数 / **一键导出诊断报告**（不含隐私内容）。

### 5.5 iCloud 账号变更

监听 `CKAccountChangedNotification`。用户退出或切换账号时**必须明确提示**，不得静默切换数据集。

### 5.6 待定：同步半到时定格的当日应做集合会残缺

**开真实同步（第 3 卷）之前必须定案。**

`DaySnapshot.requiredItemIDs` 是裸 `[UUID]`，不是关系。CloudKit 把 `DaySnapshot` 与
`PracticeItem` 当两种独立记录类型同步，**不保证到达顺序，也没有引用完整性**。于是：

**读侧**（已在第 2 卷 Task 8 处理）：快照先到、定课未到时，那几项画不出来。
`TodayViewModel` 把它们记进 `unresolvedItemIDs` 并留在三态判定的分母里，
降级成「未圆满」而非「圆满 / 无课」——错在保守那一侧。同步补齐后自愈。

**第 5 卷的月历与统计必须做同样的降级。** 它们对**历史**日期重算三态，
同样会遇到「快照登记了、本机没有该定课」。今日页降级后用户等一会儿就自愈了，
历史日期没有这个心理预期：用户会看到某个月里凭空几天不计入分母、
连续天数莫名断掉或莫名接上——**而且方向是「多」**（判成无课日就等于替他抹掉一天欠账），
比今日页那次更难被发现。要么复用 `unresolvedItemIDs` 这套降级，要么在此另立口径并写明。

**第三种到达顺序（待验证）**：`PracticeSession` 先于它的 `PracticeItem` 到达。
`PracticeSession.item` 是关系不是裸 id，同步窗口内可能暂时解析不出来而为 `nil`，
而 `DayLedger.sessions(on:itemID:)` 的 `$0.item?.id == itemID` 会把孤儿流水**全部滤掉**
（`PracticeSession.swift` 的注释写明了「孤儿流水不进任何 per-item 统计」）。
后果是当天 `total` 偏低、该圆满的报未圆满——方向是「丢」，且自愈。
其中「滤掉 ⇒ total 偏低」是读代码即得的确定结论；
「CloudKit 真会产生暂时为 `nil` 的关系」**需要真容器才能验证**，第 3 卷排查时一并验。

**写侧**（尚未处理，需定案）：反过来，`PracticeItem` 先到一半、当日还没有任何快照时，
用户此刻打开今日页，`DayLedger.plan` 会用**当时本机仅有的那部分**建快照并落库。
剩下的项稍后到达，但 `existingPlan` 已非 nil，`plan` 再也不会补——
**这一天的应做集合就永久少了几项，并同步到所有设备**。
后果是当天的圆满来得太便宜，且不可逆（快照绝不回溯改写是铁律）。

换新机、重装后首次启动是最危险的场景：没有第二台设备的快照可供并集自愈。

定案前要回答：

1. 是等 CloudKit 初次同步完成再允许定格，还是照常定格？前者要有「同步中，暂不定格」的中间态
2. 若照常定格，允不允许当日**追加**一条只含新到项的快照，交给 `merge` 的并集吸收？
   这与现有 CRDT 语义相容，但会削弱「定格」二字本身的含义
3. 追加快照的话，目标值取谁的？现行规则是「最早快照对某项毫无意见时，
   才采用含该项的最早一条快照的目标」——追加进来的项正好落在这一条上，需确认符合预期

### 5.7 待定：两台设备各撤一次同一笔，会扣两次

**开真实同步（第 3 卷）之前必须定案。与 §5.6 同批。**

`DayLedger.revoke` 追加一笔 `.adjustment` 负数来撤销，幂等键是备注里的
`revoke:<原记录 id>`。它**只在本地库里查这个键**：查到就返回既有那笔，查不到就新建。

离线时两台设备各撤销同一笔 500，各自查本地都查不到 → 各建一笔
`amount: -500`、`note: "revoke:<同一个 id>"`、**但 UUID 不同**的调整流水。
CloudKit 合并后两笔都在，而**读侧没有任何按 note 去重的逻辑**：

```
+500（真念的）  +300（真念的）  −500  −500  =  −200
```

`total` 把负数 clamp 成 0，用户看到「今天 0 声」。
**他真念的那 300 声就这么没了，而且账面上看不出哪儿出了错。**

方向是「丢」，且是最难察觉的一种：没有任何提示，数字只是变小了。

三个待答：

1. **去重放读侧还是写侧？** 读侧（`total`/`rawTotal`/`sessions` 遇到同 note 的
   `.adjustment` 只认一笔）改动集中、对历史数据也有效；写侧要靠确定性 UUID，
   而 SwiftData + CloudKit 的记录名由框架自己生成，同 `id` 属性并不会被合并成一条。
   **倾向读侧**——`note` 已经是够用的键，不需要再造一个。
2. **已经写进库的重复调整怎么办？** 读侧去重天然覆盖存量，写侧方案则需要一次清理迁移。
3. **同一笔被「撤销、又撤销那次撤销」怎么算？** 现在靠 `.adjustment` 里的正数实现，
   去重逻辑不能把这条正当路径一并吃掉。

⚠️ `Tests/ManualEntryViewModelTests.swift` 的 `重复修正同一笔不会扣两次`
**走不到这条路**——它是同一个 context 的顺序调用，第二次进来时第一笔已在本地库里。
真要验得有真实 CloudKit 合并。别看着那条测试是绿的就以为这里已经堵上了。


## 6. 界面与交互

### 6.1 今日

当天应做功课列表（进度环 / 名称 / 目标 / 当前量），已达标显示「圆满」（**文字 + 颜色，不只靠颜色**），底部常驻备份状态条。

### 6.2 计数器

- **整屏可点**，每点 +1。竞品缩小点击区后被明确差评，这是刚需
- 数字用 `.monospacedDigit()` —— 否则 1→2 时整行左右抖动
- **音效 + 震动各自可独立开关**。这是**防漏记多记的功能性反馈**，不是装饰
- 音效使用 `.ambient` + `mixWithOthers`，**否则会打断用户正在播放的念佛机**
- 撤销 −1 按钮，点击区 ≥44pt（长辈模式下更大）
- **结束时才写入一笔 Session**
- 结束/返回控件区域**不参与计数**

### 6.3 计时器

- 必须基于 `now − startedAt` **时间戳差值**，不能依赖运行时 Timer（App 挂起后 Timer 会停）
- v1 不做 Live Activity（§2.2）

**待定（用户 2026-07-29 提出，第二卷 Task 10/16 之前需定案）**：打坐希望**既能正计时、也能倒计时**，
下坐时**引磬响一声**。目前 §6.3 与实施计划都只有正计时、无声音。定案前要回答：

- 倒计时到零后是自动入账，还是仍要用户确认？（关系到「一声都不能多」——自动入账意味着人不在场也记）
- App 在后台/锁屏时到零怎么办？引磬要响就得走本地通知，那是一套单独的权限与调度
- 静音档位下响不响？（引磬是功课的一部分，但在办公室突然出声与 §6.5 隐藏模式的隐私诉求直接冲突）
- 倒计时时长的预设档位取哪几档

### 6.4 手动补记与修正

**并列的第三种录入方式**，不是次要功能——很多人修完才想起来记。竞品差评证明「改错数字」找不到入口是真实痛点，**修正入口必须显眼**。

- 可指定**任意历史日期**
- `dayKey` 为所选日期，`tzOffsetMinutes` 为当前时区偏移
- 补记历史日期时，若该日 `DaySnapshot` 不存在则按当日配置补建；**若已存在则沿用，绝不覆盖**

### 6.5 隐藏模式

> 原名「禅modo」。**动机不是护眼，是宗教身份隐私。**

竞品评论中两条独立诉求，动机完全一致：

> 「能不能加个黑暗模式——界面全黑只有小数字？**因为念佛号不想让别人知道，比如开大会的时候**」
> 「希望增加隐藏模式，人多的时候不显示背景只显示数字。**工作关系，不能让同事知道自己念佛**」

**设计**：

- 界面切纯黑 `#000`，只留一个极暗的大号数字：`#8A7A66` on `#000` = 5.06:1
- **不显示任何佛教符号、App 名称、经咒名** —— 隐私是第一目标，旁人瞥见只是个数字
- `isIdleTimerDisabled = true` 阻止自动锁屏（阅读/导航类标准用法）
- **整屏可点**，装在兜里或垂手也能按
- `preferredScreenEdgesDeferringSystemGestures = [.bottom, .top]` 防误退
- 底部安全区不参与计数

OLED 纯黑像素不发光，耗电极低。此模式无滚动，可用纯黑。

**已废弃的相关设计**：
- 「锁屏后继续计数」— iOS 上做不到，靠后台音频保活会被拒审。**注意：Apple Watch 上可以**——苹果为 silent meditation 专设了 `mindfulness` 扩展运行会话，熄屏不中断、上限 1 小时（§8.6）
- 音量键计数 — 有审核风险（尽管市面存在此类 App）
- 蓝牙响指器 — 便宜快门器多发 HID 音量键会被系统吃掉，未实测不写进 v1

### 6.6 定课管理

新建（模板或自定义）/ 修改 / 拖拽排序 / 归档。支持**自定义经咒名称**——竞品高频诉求。

> **修改目标值不影响历史圆满判定**（§4.2 DaySnapshot）。这一点须在 UI 上明示，否则用户会担心「改了目标以前的记录是不是就废了」。

#### 内置模板清单

取自三款竞品 App Store 描述的**交叉验证**（万物叁仟 / 八万四千 / 一念计数），非臆测：

| 类目 | 计量 | 说明 |
|---|---|---|
| 念佛（佛号） | 计数 | 阿弥陀佛、观世音菩萨等圣号 |
| **持咒** | 计数 | **三款竞品均为一等公民，评论中大悲咒/心咒/往生咒高频。v2.0 前的范围遗漏** |
| 诵经 | 计数（遍/部） | 心经、金刚经、地藏经、普门品等 |
| 拜佛（顶礼） | 计数 | |
| 打坐（禅坐） | 计时 | |
| **抄经** | 计时或计数 | **同为遗漏项** |
| 供养（供灯/供水/供香） | 勾选 | |
| 放生 / 布施 | 勾选或计数 | |

模板只预置**名称与计量方式**，不预置经文内容（避免版权与体积），亦不预置目标值（见下）。

#### 不预设目标值

**证据**：9 款竞品描述全部为「可自定义功课目标」「设定发心目标」，**无一款给出预设数字**。

这不是市场疏忽，是教义约束——定课量因人而异，印光大师所倡「随分随力」即此意。App 替用户设定「念佛该念 5000 声」既无依据，也可能造成压力，与本产品定位直接冲突。

因此：新建定课时目标值默认**留空**（= 不设目标，只记录累计，仍可正常计数与查看统计）。旁边给一行**可选**的快捷 chip：`108` `1080` `不设目标`。

- `108` 是唯一有客观依据的数字——一串念珠即 108 颗，全样本唯一的用户自述目标为「每天目标佛号 5000 声 / 心经 49 遍」（1 例，不足以泛化为默认值）
- 文案须明确「**不设目标也完全可以用**」

#### 批量增加

竞品「佛号计数器」（评论最多的一款，490 条）提供 `+1 / +5 / +10 / +50 / +100 / +500 / +1000`。

**这是市场标配，且有真实场景**：拨完一串念珠一次加 108，或从实体计数器誊抄。v1 须支持：长按主计数区（或计数页次级按钮）唤出批量增加，预设 `+108`，可自定义步长。缺此项会被直接对比出劣势。

### 6.7 回顾与统计

- 月历热力图四档：无 / 少许 / 过半 / 圆满
- 初一十五、十斋日用**描边标记**，不用文字
- 格子视觉 40pt，**hitSlop 撑到 44pt**
- 点击某日看当天所有流水明细（含来源设备）

**主指标是「累计」，不是「连续天数」。**

「不制造焦虑」与 streak 是自相矛盾的——连续 200 天断掉那一刻，正是要避免的焦虑，且加倍。而竞品评论证明用户本就在意累计（「观音心咒的功课是在九位数」）。

| 指标 | 位置 |
|---|---|
| **累计念佛 X 声 / 累计圆满 X 天** | **首页大字。只增不减，永不惩罚，契合「积累福德」语境** |
| 近 30 天圆满 X 天（滚动窗口） | 次级。断一天不归零 |
| 连续天数 | 降级到「我的」页一个安静的小数字 |

断课时**绝不显示红色的「0 天」**。

### 6.8 圆满日的三态

不是二元的：

| 状态 | 含义 | 计入？ |
|---|---|---|
| 圆满 | 应做的都达标 | ✅ |
| 未圆满 | 有应做未达标 | ❌ |
| **无课** | **应做集合为空**（如全是初一十五，而今天是初七） | **不计入分母，不中断** |

### 6.9 长辈模式

竞品好评出现「即使不会使用智能手机的老年人也会使用了」。**年长居士是主力人群之一，不是边缘情况。**

一个开关，同时放大字号、点击区、行距，并简化今日页（只留计数，隐藏统计入口）。**引导流程中主动询问，而非藏在设置深处。**

### 6.10 首次启动

三件事，**都可跳过**：

1. 选内置模板（**只选类目，不强制设目标**；目标留空即可开始用——见 §6.6「不预设目标值」）
2. **iCloud 状态说明** —— 已登录说明「记录会自动备份，换手机也不丢」；未登录说明「App 完全可用，登录后自动补传」。**不得强制或诱导登录**
3. 提醒时间 + 是否开启长辈模式

### 6.11 负数与孤儿防御

adjustment 可能让求和为负 → **显示层 clamp 到 0，账本保留原值**。
`session.item` 可能短暂为 nil（同步时序）→ 所有读取路径必须防御。

### 6.12 迁移

用户手上已有别的计数器或纸本功课表。除手动补记外无导入通道，这是真实迁移摩擦。v1 至少在文案上正视：引导用户**把历史累计数一次性补记为一笔起始流水**。

## 7. 视觉规范

### 7.1 基调

**宁静、放松、正能量**，三个词分开处理：

- **宁静** — 减法：去卡片描边、去图标底板、细线宽、疏排字距、慢动效
- **放松** — 圆角 16–20px、线宽 2.5–3px、字重 400、字距收敛
- **正能量** — **只用光、生、圆满三种语言**：晨曦暖调、从枯到生的绿阶、安静的「今日圆满」画面

### 7.2 色板

所有值经对比度验算。**不使用 `opacity` 派生层级**——用透明度调淡等于绕过色板审计（早期版本曾因此产生 6 级低于 3:1 的文字，最糟的 Tab 标签仅 2.04:1）。

**浅色 · 晨光暖白**（底 `#FAF7F0`）

| 用途 | 色值 | 对比度 |
|---|---|---|
| 正文 · 数字 | `#2B2620` | 14.01:1 |
| 次要 | `#5E5647` | 6.77:1 |
| 最弱文字层 | `#6F6759` | 5.22:1 |
| 主色 赭石 | `#A05B35` | 4.86:1 |
| 圆满 生机绿 | `#5C7652` | 4.71:1 |
| 晨曦金（光晕） | `#D9B679` | 非文字 |

**深色 · 夜课暖黑**（底 `#17140F`，非纯黑，避免 OLED 滚动拖影）

| 用途 | 色值 | 对比度 |
|---|---|---|
| 正文 | `#EFE9DC` | 15.18:1 |
| 次要 | `#B0A897` | 7.78:1 |
| 最弱文字层 | `#9C9385` | 6.06:1 |
| 赭石 | `#C98A5E` | 6.37:1 |
| 绿 | `#93A886` | 7.16:1 |

**硬约束**

1. **最弱文字层到此为止，不得再淡**
2. **晨曦金光晕封顶 12%** —— 实测叠加 16% 时赭石跌到 4.46:1。赭石文字不得出现在光晕最浓处
3. 深浅两套**各自独立验算**
4. **绿色不可作为唯一状态指示**，须配文字「圆满」

### 7.3 字体

**不套用西文配对。** 设计工具推荐的 Lora / Raleway 在中文场景**一个字都不渲染**，会静默回落系统字体。

界面 PingFang SC（走 Dynamic Type）/ 经文回向 Songti SC / 数字圆体 + **`.monospacedDigit()`**

### 7.4 动效

微交互 150–300ms；遵循 `accessibilityReduceMotion`；**无限循环动画只用于加载指示**（早期版本曾在今日页放 6 秒呼吸光晕，纯装饰的无限动画持续牵引注意力，与「宁静」自相矛盾，已删除）。

### 7.5 深浅模式切换

**四选项**：跟随系统 / 浅色 / 深色 / 按时间自动。默认跟随系统。仅按时间违反系统预期，也伤害畏光用户。

## 8. 平台集成

### 8.1 本地通知

- iOS 本地通知**上限 64 条**。多定课项 × 多时间 × 农历排班很容易撑爆
- 必须**滚动窗口调度**：只排未来 N 天，启动/进前台时补排
- 当天已达标的功课**主动 cancel** 剩余提醒
- 农历用 `Calendar(identifier: .chinese)`。支持初一十五、**十斋日、佛诞日**（用户主动要求）

### 8.2 交互式桌面小组件（v1 前三优先级）

这个 App 没内容、没社交、没推荐流，**第 30 天用户还打开它的唯一动力是他自己的纪律**。产品能做的只有一件事：**把摩擦降到零，然后消失。**

iOS 17 起小组件支持 `Button(intent:)` —— **不打开 App，直接在桌面点一下 +1 / 勾一课**。竞品已实现（「现在可以直接在桌面操作小组件来加减数字」），**这已是入场券，不是加分项**。

- 读 App Group UserDefaults 本地缓存（§4.4）
- 写入需处理 append-only 的 dayKey / 时区 / 草稿去重
- Timeline 按「**下一个一日起始时刻**」刷新，正确处理跨零点
- 缓存携带 `dayKey`，与当前不符时显示「待刷新」而非过期数据
- 适合快速 +1 与勾选，不适合整段计数会话

### 8.3 提醒是唯一召回触发器

因此基础每日提醒**不可砍**。

### 8.4 隐私锁

Face ID / Touch ID，**必须有设备 Passcode 兜底**。

> 定位同 §6.5：防的不是黑客，是同事和家人看到「你在念佛」。

### 8.5 导出

v1 只做 **JSON**（「永不丢」的备份网）。CSV 推到 1.1。

### 8.6 Apple Watch（1.1，排在 iPad 之前）

> 本节所有平台能力均已查证 Apple 官方文档确认，非推断。

#### 为什么 Watch 不是「多一个平台」

竞品「万物叁仟」配套实体硬件「叁仟计」，评论中出现「**等我买了三千计数的就不用你了**」。

**真正的竞争对手是实体计数器，不是别的 App。** 用户要的是「不用看、抬手就点」的手感。Watch 是 iOS 生态里唯一接近它的形态——这也解释了为何 Watch 诉求（4 条）远高于 iPad（1 条）。

#### 核心交互：数字表冠即念珠

念珠的用法是**拇指推一颗、念一句，有段落感，且不用看**——眼睛可以闭着。

数字表冠转动有物理段落，`digitalCrownRotation`（watchOS 6.0+）的 `isHapticFeedbackEnabled` 参数**每一格给一次触感**。拨一颗珠 ≈ 转一格，映射近乎一比一。

**这是 iPhone 永远给不了的**：iPhone 必须睁眼看着屏幕点。

保留整屏点击作为并存输入（同 §6.4）。

#### `mindfulness` 扩展运行会话

iPhone 版被迫放弃的「熄屏后继续计数」（§6.5 已废弃项），**在 Watch 上苹果专门开了口子**：

> `mindfulness` — Enables extended runtime sessions for **silent meditation**.（`WKBackgroundModes` 官方文档原文）

| 属性 | 值 |
|---|---|
| 运行方式 | 前台（frontmost） |
| **时长上限** | **1 小时** |
| 熄屏 | **不中断**——"The watch screen doesn't need to remain on to keep your app alive" |
| 熄屏期间 | 可继续播放触感、处理数据 |

**这不是钻空子**。苹果明写「按 app 的用途选类型，不要按会话提供的功能选」——念佛打坐本身即 silent meditation，用途完全对应，过审无虞。

**三个必须处理的坑**：

1. ⚠️ **按下表冠 = 用户主动离开 = 会话终止**，而我们正用表冠**转动**计数。转动无碍，但误按会断 → **`WKExtendedRuntimeSessionDelegate` 的 invalidate 回调必须立即落账**，一条流水都不能丢
2. ⚠️ **每个 app 只能声明一种**扩展运行类型
3. ⚠️ 经行念佛（边走边念）苹果建议改用 workout session——**但那需要 HealthKit 权限，与「不收集任何数据」的定位直接冲突。不做**

另需注意：持续高 CPU 会被系统取消会话。计数器负载极低，不构成风险。

#### 数据同步：append-only 的红利在此兑现

**加 Watch 不需要任何新的冲突处理**——这是 §4 架构决策最大的一笔回报。

每笔流水独立 UUID，两端各自 append，求和即得。

> 反证：若当初存的是「总数」字段，手表记 300、手机记 500，CloudKit 整记录级 LWW 会让你**只剩 500**。

因幂等，两条通道可同时开启，重复投递无害：

| 通道 | 角色 | 代价 |
|---|---|---|
| **CloudKit**（SwiftData，**已确认 watchOS 10.0 起可用**） | 骨干；手机不在身边也能同步 | watchOS 上同步显著更慢 |
| **WatchConnectivity** `transferUserInfo` | 快速通道；FIFO 保证送达 | 需手机可达 |

#### 表盘复杂功能：一个硬限制

WidgetKit 自 watchOS 9.0 起可用，可做「抬手即见今日计数」。

⚠️ **但交互式按钮/开关只支持 iPhone 与 iPad**（官方文档适用范围明写 "on iPhone and iPad"）。**watchOS 复杂功能点击只能打开 App，无法直接 +1。**

即 §8.2 那套「小组件内直接计数」的体验**在 Watch 上无法复制**。缓解：Watch 打开 App 本身极快。

#### 隐私是白送的

Watch 屏幕旁人无从窥见。§6.5 那两条「不能让同事知道自己念佛」的诉求，**在 Watch 上无需任何设计即已成立**。

#### 代价（不可低估）

- **独立 target，UI 基本重写**——「同一套 SwiftUI」是幻觉，Watch 布局逻辑完全不同
- **测试面翻倍**，而 §10.2 定的唯一硬指标正是崩溃率与数据丢失
- **watchOS 的 CloudKit 同步实测比 iOS 更不稳**，「永不丢」的承诺在 Watch 上更难兑现
- **必须真机验证**：表冠触感、扩展运行会话、常亮显示，模拟器均无法测试

#### 为什么仍排在 v1.1 而非 v1

不是因为 Watch 不重要，恰恰相反——**正因它是这个 App 的终极形态，更不能在 iPhone 端尚未稳固时仓促推出。**

唯一硬指标是崩溃率 < 0.1% 与数据丢失 = 0（§10.2）。Watch 翻倍的测试面会直接威胁该指标。**先把 iPhone 端做成磐石。**

**「慧行 WiseWalk」没有任何目标用户会去搜。** 名字可保留，但必须由描述承担全部搜索职责：

| 字段 | 内容 |
|---|---|

### 9.2 前 1000 个用户

唯一可行渠道是**紧密宗教社群的口碑**：寺院共修微信群、佛教论坛、豆瓣小组。宗教社群的信任传播极强。

> **因此需要一个克制的分享入口。** 早期版本把所有分享一并砍掉，理由是反攀比——但「分享一个清净的法工具」与「排行榜攀比」是两码事，佛教徒本就有主动传播好工具的习惯。**砍掉分享等于掐断唯一的有机增长渠道。**
>
> 形式：分享 App 本身、或一张不含具体数字的回向卡。**绝不分享排名或与他人比较的内容。**

### 9.3 发心页

宗教用户极在意「谁做的、图什么」。一页明说：**法布施、不收集任何数据、无广告、永久免费、数据只在你自己的 iCloud 里**。

隐私架构本身就是营销资产（60 条评论在感谢竞品「没有广告」）——必须显性表达，而不是埋在技术选型里。

**同时必须说清成本结构**，否则「永久免费」听起来像空头支票：一句话讲明「这个 App 没有服务器，你的数据存在你自己的 iCloud 里，所以它不烧钱，也就不会有哪天撑不下去关掉服务器的事」（依据见 §10.6）。这比任何承诺都有说服力。

### 9.4 不设赞赏入口

法布施定位下，用户一定会想「随喜功德」——竞品评论里就有「随喜开发者功德」。**但仍然不做赞赏/供养入口**，三个理由：

1. **平台规则的尴尬**：App Store 内的打赏属数字内容，必须走 IAP，**苹果抽成 30%**。「供养」被平台抽三成，在宗教语境里说不过去
2. **破坏核心信任资产**：「我不图你什么」是本产品最强的差异化（对比竞品的广告与服务器焦虑）。一旦出现收款入口，这句话的分量立刻打折
3. **法布施的回向本就不是钱**

**替代方案**：在想放赞赏的位置，放「**转给需要的人**」。把随喜之心导向传播而非金钱——这既契合法布施，又正好是 §9.2 认定的唯一有机增长渠道。

### 9.5 繁体中文

台港及海外汉传居士，近乎零成本可及。

## 10. 成功标准与可持续性

**本项目定位为法布施：无偿、不求回报、不以增长为目的。**

这不是「免费」的同义词，而是一条约束——它决定了哪些指标可以看，哪些指标**一旦当成目标就会把产品带坏**。

### 10.1 被禁止作为目标的指标

| 指标 | 为什么不能当目标 |
|---|---|
| DAU / 留存率 | 一旦盯它，就会去做推送轰炸、streak、排行榜——**正是本产品已明确砍掉的东西**（§6.7）。古德哈特定律在这里的代价是让人对修行产生焦虑 |
| 下载量 | 法布施的圆满不在人数。**十个人真正受益，与十万人下载后卸载，前者是成功** |
| 使用时长 | 见 §10.3，这是反指标 |
| 评分 / 好评数 | 可以看，**不可以追求**。绝不做评分弹窗诱导——那是在打断别人的功课 |

> 这些数据仍应从 App Store Connect 读取用于**判断是否造成了伤害**，但不设增长目标，不为其做产品决策。

### 10.2 唯一必须盯死的硬指标

**崩溃率与数据丢失率。**

理由不是商业的：竞品头号差评是闪退（36.7%），而在这个场景下，闪退意味着**弄丢别人的功课**。用户对着一个「帮助修行」的工具，丢了三年的念佛记录——这不是体验问题，是造违缘。**做不好，不如不做。**

| 指标 | 判定线 | 来源 |
|---|---|---|
| 崩溃率 | **< 0.1% 会话**。超过 0.5% 停止一切新功能，全员修 bug | MetricKit / Xcode Organizer |
| 数据丢失 | **0。一例都算严重事故** | 用户来信 + 同步诊断页 |
| 冷启动到可计数 | < 1 秒 | MetricKit |

### 10.3 反指标（越低越好）

法布施的工具，**理想状态是用户尽快用完就走，回到修行本身**。

| 反指标 | 目标 |
|---|---|
| 单次使用时长（计数场景除外） | 越短越好。「打开到记完的耗时」是第一产品指标（§2.1） |
| 我们主动发出的通知条数 | 只有用户自己设的提醒。**零运营推送、零功能公告、零节日营销** |
| 首次启动到可用的步骤数 | ≤ 3，且全部可跳过 |

### 10.4 真正的成功信号（定性）

没有数值。只有一条：

> **收到真诚的「这个 App 帮我把定课坚持下来了」。**

一条就够。这就是法布施的回向。

### 10.5 什么时候停止打磨

原问题「什么时候该承认没人要」**在法布施框架下不成立**——用户少不是失败。

替换为两条真正的停止条件：

- **停止加功能**：v1 核心闭环（打开 → 看到今天做什么 → 点一下 → 完成）稳定无崩溃后即停。**此后每一个新功能都要先回答「这是在帮人修行，还是在帮我自己找事做」**
- **停止项目**：只有在「继续维护会造成伤害」时——比如无力修复会丢数据的 bug。此时的正确动作不是弃置不管，而是走 §10.6 的退出预案

### 10.6 可持续性：我自己撑得下去吗

**这是必须自问的问题。** §1.1 的价值主张是「我不做服务器，所以不会因为撑不下去而弄丢你的功课」——那就必须证明自己不会重蹈八万四千的覆辙。

**成本结构（法布施能否长期成立的关键）**：

| 项 | 成本 | 是否随用户数增长 |
|---|---|---|
| 服务器 | **¥0（没有服务器）** | — |
| CloudKit 存储 | **¥0** | **否。私有数据库占用的是每个用户自己的 iCloud 配额，不是开发者配额** |
| Apple 开发者账号 | **$99/年** | 否 |

**结论：唯一的经常性成本是每年 $99，且与用户规模完全无关。** 这是零后端架构在法布施场景下最被低估的优势——十个用户和十万个用户，成本一样。

**但风险仍然存在**，必须诚实对待：

| 风险 | 后果 | 缓解 |
|---|---|---|
| 开发者账号断缴 | App 从 App Store 下架。**已安装用户可继续使用，不会被远程删除**，但无法重装、换手机拿不回来 | 数据导出必须做到位（§2.1 自动备份到「文件」App），用户任何时候都能带走全部数据 |
| 作者失去精力 / 无力维护 | 系统更新后逐渐不可用 | **GPL-3.0 开源（§10.7）**，任何人可 fork 自用 |
| 作者不在了 | 同上 | 同上 |

**数据导出因此不是附加功能，是法布施的伦理底线**：既然我劝人把功课托付给这个 App，就必须保证他随时可以完整地拿走。

### 10.7 开源：GPL-3.0，且必须保持独占版权

**决定：代码以 GPL-3.0 开源，官方版本仍由作者上架 App Store。**

#### 先说清楚一个坑

**GPL-3.0 与 App Store 条款公认冲突。** VLC 曾于 2011 年因此被下架，后改用 LGPL 才得以回归。冲突点：GPL 禁止施加「附加限制」，而 App Store 的 DRM 与设备数限制正属此类。

**但这个冲突约束不到你**，因为——

> **版权人不受自己所授许可的约束。** GPL 是你授予他人的条款，不是套在自己身上的枷锁。你拥有 100% 版权，就可以同时把代码以 GPL-3.0 放上 GitHub，并以任意条款把自己的构建产物上架 App Store。

#### 于是产生一个罕见的好结果

对**套壳者**而言，GPL-3.0 恰恰是 iOS 平台上最强的反制：

| 套壳者的处境 | 结果 |
|---|---|
| 拿代码闭源加广告上架 | 违反 GPL-3.0 → 可发 DMCA 通知要求苹果下架 |
| 老实遵守 GPL 开源后上架 | **仍然违反 App Store 条款**（同 VLC）→ 依然上不了架 |

**两条路都堵死。** 换用 MIT / Apache-2.0 则完全不设防，MPL-2.0 只做文件级 copyleft、挡不住「新文件里加广告」。**GPL-3.0 在这里是唯一同时满足「布施代码」与「防套壳」的选择。**

#### 两个必须守住的前提

这套逻辑完全建立在「你独占版权」之上，一旦破坏即失效：

1. **不合并任何外部 PR**（除非签 CLA 转让版权）。一旦掺入他人的 GPL 代码，你就不再是唯一版权人，**自己上架 App Store 立刻变成侵权**
   - 与已定的「仅公开代码，不承诺回复 issue/PR」正好互为因果——**这不只是省精力，是法律必需**
2. **所有第三方依赖必须是宽松许可**（MIT / Apache-2.0 / BSD）。**引入任何 GPL/LGPL 依赖都会摧毁上述结构**。依赖清单需在上架前逐条核对（§11）

#### README 需明说

- 本仓库为法布施，GPL-3.0
- **不接受 PR，不承诺回复 issue**；欢迎 fork 自用
- 官方构建由版权人发布于 App Store；**你 fork 后的版本受 GPL 约束，因而无法上架 App Store**——这不是刁难，是 GPL 与苹果条款的既有冲突
- 想帮忙最好的方式：转给需要的人

## 13. 三轮评审确认无需改动的决策

实现时**不要「优化」掉**：

1. **append-only 流水求和**（CRDT PN-Counter）—— 整套方案最坚实的地基
2. **结束时才写一笔 Session**，不做 per-count —— 性能不是真问题，这份克制要保持
3. **dayKey 存整数** —— 抗时区漂移
4. **定课项归档不真删** —— 避免孤儿流水
5. **圆满日三态**（§6.8）
6. **砍掉排行榜 / 徽章 / 彩带 / 红点**的克制
7. **砍掉熄屏计数 / 音量键 / 蓝牙响指器** —— 务实且避免被拒
8. **§4.7 诚实声明「并非全无冲突」**
9. **JSON 导出作为备份网**
10. **设置走 AppStorage + KVS**，不进数据库

**已结**：§10 成功标准 → 定位为**法布施**，§10 整节据此重写；开源 → **GPL-3.0**（§10.7）。

### 14.3 本轮新发现的战略推论

竞品「万物叁仟」配套硬件「叁仟计」智能念佛计数器，且评论中出现「**等我买了三千计数的就不用你了**」。

**真正的竞争对手不是别的 App，是实体计数器。** 用户要的是「抬手就点、不用解锁、不看屏幕」的手感。这条同时解释了为什么 Apple Watch 诉求（4 条）高于 iPad（1 条）——Watch 是 iOS 生态里最接近实体计数器的形态。若日后做 Watch，这是核心论据。
